# 智能路由故障三次确认

智能路由的真实文本请求遇到可重试的快速瞬态故障时，BridgeOps 在同一渠道和分组内最多尝试 3 次。前两次失败、第三次恢复时仍使用原候选，不显示“故障回退”，也不增加路由故障计数。连续 3 次均失败后原子记录这 3 次物理路由故障，当前候选立即进入无倒计时的故障隔离，并继续尝试下一个可用候选；隔离不会因时间经过而自动释放，只有连续 3 次恢复探测成功才自动恢复真实智能流量。智能文本请求不设固定首字截止；等待期间每 30 秒安排一次共享的同目标健康检查，检查从实际派发开始最多等待两分钟。检查超时后，未受理请求直接退出当前候选，不再对该超时做同候选三次确认；已经受理的请求只终止、不重发。预派发受管 Key 容量、本机并发准入、确定性请求/模型不兼容、上下文限制、`402`/账户不可用、永久或未知协议/状态错误仍按各自规则直接选择下一候选。只有全部候选都失败时才向下游返回最终脱敏错误或协议合法的重试提示。

手动固定路由不进入上述流程。它只向配置的单一渠道/分组发起一次请求，不使用智能首字预算、同候选三次确认、候选回退、路由故障/冷却或会话亲和。慢首字可被动记录，但不能中止固定请求、显示雪花或改写智能路由状态。客户端取消、错误脱敏、明确的 401/403 Key 失效与确定性模型能力事实更新仍保留。

可重试范围包括瞬态网络错误、EOF、结构化识别为瞬态的首输出前 SSE 或非流式 JSON 错误，以及 HTTP 408、409、425、429 和标准 5xx（500 到 599）。上游有时会用 HTTP 200 包装 `{"error": ...}`；它必须在写给下游、标记渠道健康或记录成功前按同一结构化规则分类，不能因外层 200 被透传为成功。SSE 或 JSON 中的 Anthropic `api_error`、`overloaded_error`、`rate_limit_error`、`stream_read_error`，明确的超时/服务不可用/服务端错误，以及内嵌 408、409、425、429、标准 5xx 状态属于瞬态；根级或嵌套数值 `code` 同样按 HTTP 状态分类，600 及以上的非标准状态不冒充服务端瞬态错误。`error: null`、空字符串、空对象、空数组和 `false` 不表示错误；Responses 只有 `response.status: "failed"` 或非空 `response.error` 才算失败。`invalid_request`、鉴权/权限、`billing_error`、`request_too_large`、`insufficient_quota`、工具/内容策略、模型不支持和未知错误不重放、也不写入路由健康，但在尚未受理时可以按确定性失败规则尝试下一候选。HTTP 200 包装或 SSE 结构化错误中的内嵌 401/403、`authentication_error` 或明确失效 Key 标识都要走 Key 失效流程；确认模型不支持则写入模型能力负缓存，避免再次选中。402、上下文超限、明确账户容量和永久配置错误直接处理，不重复当前候选。上游一旦返回确定性的永久 3xx/4xx，即使随后读取错误正文失败，或者正文内含 `overloaded` 等瞬态词，也只能以外层 HTTP 状态为准，单次换候选并保留审计，不得降级为 transport 重放或污染冷却。快速错误仍按上述三次确认处理，慢响应由等待健康检查判断，不因 30 秒或亲和场景的 90 秒无正文而切换。检查在途时不叠加，完成后间隔 30 秒再安排；本机并发不足导致的跳过不计渠道故障。流式首个有效输出、非流式首个实际正文字节到达后停止等待检查；后续生成和完整读取没有该检查的总耗时截止，非流式正文仍须完整缓存后才发送给下游。收到可信受理生命周期、正文、思考或工具调用后，以及已派发的图片请求，始终禁止同候选重放和跨候选回退。

管理员使用记录按首字延迟分级显示。只有 `first_byte_ms > 30000`、日志中保存了真实渠道与分组，且规范化 `route_reason` 为 `smart_primary`、`fallback`、`session_affinity` 或 `model_filtered` 时才显示雪花按钮。固定路由、内部请求、空值和未知的未来路由原因默认失败关闭，不显示雪花，服务端也拒绝创建冷却。点击后浏览器只发送请求日志 ID 与 `Idempotency-Key`，服务端在事务内锁定请求日志、解析当时实际命中的渠道/分组并写入 `gateway_manual_routing_cooldown_audits`。前端提供的渠道或分组字段一律不参与决策。相同请求日志与幂等键的重试返回原结果，不重复延长冷却或生成审计；成功请求也不能提前解除尚未到期的管理员手动冷却。冷却只影响智能路由，时长由 `scheduler.routingFailures.manualCooldownMinutes` 设置，默认 10 分钟，允许 1–1440 分钟。

探测配置中的冷却分组提供“一键启用”。请求必须携带稳定 `upstream_group_id`、当前 `presence_generation`
和 `Idempotency-Key`；服务端在同一事务内复核分组仍 present、代次未变化且本地上游 Key 已启用、
非 provisioning 并具有可用密文，然后只清除该规范分组当前代次的自适应失败链和冷却。Key 缺失、
停用或仍在创建时拒绝执行，不能借此修复或绕过结构门禁。每次有效操作追加
`gateway_routing_enable_audits`，保存操作者、原因、原失败状态、原冷却截止时间和 generation；相同幂等键
只返回原结果。若解除的是 `manual_cooldown`，原 `gateway_manual_routing_cooldown_audits` 必须保留，
新审计只表达管理员后来显式覆盖了该冷却，不能修改或删除旧证据。

结构化认证错误的 `error` 既可能是对象，也可能直接是 `"authentication_error"`、`"invalid_api_key"` 等字符串标识。两种形态必须经过相同的 Key 失效判断，并分别保留非流式 JSON 与 SSE 集成测试，不能只完成本次回退后让失效 Key 继续参与后续路由。

故障隔离恢复探测同样要求三个结果一致。连续三次成功才允许清除该组已有的路由故障并恢复真实流量；连续三次可隔离失败原子写入三次物理路由故障并保持隔离；三次中同时出现成功和失败时，本轮没有结论，不改变隔离，并在持久化的短 `next_probe_at` 到期后重新探测。探测计划只按 `next_probe_at` 推进，不存在冷却释放倒计时，也不能因为隔离时间已经很长而绕过三连成功。429 可以确认重试，但不会冷却整个渠道，且不能因快速复测放大上游限流。调用方取消和明确业务错误不计为探测故障。此类请求仍以 `route_reason=latency_probe` 记录为内部流量；健康分组没有主动探测，真实网关请求只被动记录延迟。

调度查询只选择仍处于冷却（`CoolingDown=true`）、且路由状态与当前稳定上游分组 ID 和 `presence_generation` 精确匹配的恢复目标。健康分组、旧代状态以及仅有历史 `next_probe_at` 的分组都不能发起主动请求。`gateway_latency_probe_states` 持久化 `next_probe_at`、确认结论和确认次数，并以渠道、分组、应用及上游分组的 ID/presence generation 作为作用域；删除后同名重建的旧探测不会触碰新组。每次恢复请求都从受管分组当前代次已同步的模型 ID 或直连分组当前凭据 revision 的模型投影中自动选择模型，不读取独立探测模型配置，也不按名称猜测。历史全局、渠道和分组探测开关只为配置/API 兼容保留，不再阻止当前代次冷却恢复；调度仍过滤渠道错误和失效 Key。低余额只影响最终路由，低余额且确实处于冷却恢复阶段的候选仍可在费用预算内接受探测，明确余额不足只更新渠道事实而不写组级冷却。全局只允许一个调度轮次运行，轮次内的候选并发、候选数和费用预算均有上限。整轮超时除了覆盖三种应用、每个候选和三次确认的请求预算，还必须预留模型同步、数据库查询、日志和故障落库的管理余量，确保最后一个候选的第三次失败能够完成分类和持久化。

生图请求是例外。`/v1/images/generations` 以及 `/v1/responses` 中声明 `image_generation` 工具的请求，智能路由在发出前可以因 Key 或目标准备失败选择其他候选；固定路由的准备失败直接返回错误，不改投其他候选。请求一旦发给上游，两种模式都不得自动重发或切换渠道，因为上游可能已经受理并按次计费。智能路由中每个已发出的真实请求若发生 transport、首字超时、响应读取失败、明确瞬态 SSE 或非流式 JSON 错误，或 HTTP 408/409/425/429/5xx，只累计 1 次跨请求路由故障；401/403/402/400/404/413、跳转和永久或未知 SSE/JSON 错误不污染路由健康。连续真实失败仍按 10 分钟窗口累计，第 3 次开始进入无倒计时的故障隔离。固定路由失败不写智能路由故障或隔离。下游只收到固定脱敏错误，完整原因保留在管理员请求记录中。

使用记录的列表金额依次采用上游直报/对账金额、请求冻结价格事实计算值和后端账单展示值。以上金额尚不可用、请求没有冻结价格事实，但保存了 `group_ratio`、`completion_ratio` 和 Token 时，页面可按请求冻结倍率与默认 `500000 quota/USD` 显示“倍率估算”：未缓存输入按 `1.0x` 计价，缓存写入和读取 Token 按行业常用的 `0.1x` 缓存倍率计价，输出使用冻结输出倍率（缺失时回退输入倍率）。其中 `0.1x` 只是没有价格事实时的非权威页面展示兜底，不能代替目录中未知的缓存单价。该金额不写回数据库账单、价格事实或聚合，也不再次乘资金系数；倍率徽标始终显示请求冻结倍率，倍率费用估算只用于没有价格事实的记录，最终金额始终以上游对账为准。

文本请求优先按“精确渠道 + 规范分组 + 精确上游模型”读取自动采集的渠道目录价。渠道目录本身已包含模型输入、输出和缓存价格的差异，所有已有价格项只统一乘一次该渠道分组的有效倍率，不能再乘 `completion_ratio`。渠道价格不可用时，依次使用每 24 小时从 LiteLLM 自动同步的全局基础价和手工价格页兜底；全局基础价仍按输入/输出倍率语义计算，即输入和缓存价乘有效输入倍率，输出价乘有效输出倍率（缺失时回退输入倍率）。缓存读取和写入价可为空：相应 Token 为 0 时不阻断计算，实际 Token 大于 0 且价格未知时必须返回 `price_missing`，不能按 0 元冻结。最终价格事实绑定精确渠道、分组代次、Key 代次、模型与协议，后续目录或手工改价不改写历史请求。上游费用与系统估计费用只按相对比例比较，严格超过 `5%` 即标记，不附加绝对金额门槛。
